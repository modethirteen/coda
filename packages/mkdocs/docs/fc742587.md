## (RFC)

The following proposal is a superset of [Remix's recommendation](https://remix.run/docs/en/main/file-conventions/routes#folders-for-organization). The difference between the standard recommendation and this one is that we add a concept of shared code with `_shared` directories.

👉 Feedback will be grabbed on this Coda page: <https://coda.io/d/_dYFR3G4AskL/_su5Lw#_lun3X>

## React app directory structure

Traditionally, AppFolio has lacked a standardized convention for organizing React code. This proposal aims to provide a convention.

**As a TLDR, the proposal is made to make you think less about how to organize your code and more about learning a single convention that should be applied.**

### Problem

There are a few problems with React development today, and one of them is the lack of a convention with our directory structure. This causes:

* Inconsistent development practices due to different teams coming up with different solutions for the same problem 😊
* Poor code reusability by not having a standardized way to mark down if a component, hook, or other piece of code is reusable
* Large files due to a lack of awareness or guidance on breaking down components into smaller, manageable units
* Disorganized files due to there being no convention on when a dev should create a new directory for anything
* Scalability concerns due to the unwieldy-ness because of the structure of a project

### Proposal

Update the recommended way for organizing React code to follow the Remix folder convention with an added modification for shared code. An example of this is:

```
app/
├── routes/
|   ├── _shared <= Shared directory across all route directories
│   │   ├── hooks/
│   │   ├── utils/
│   │   ├── SharedComponent.tsx
│   │   └── MoreComponents.tsx
│   ├── payments.amount/
│   ├── ├── hooks/
│   ├── ├── utils/
│   │   ├── route.tsx <= Defines the entry point for the /payments/amount path
│   │   └── PaymentAmount.tsx
│   ├── payments.amount._shared/ <= Shared directory directories having payments.amount.
│   │   ├── ChangePaymentMethodButton.tsx
│   │   ├── PaymentAmountChoice.tsx
│   │   ├── PaymentAmountDateInput.tsx
│   │   └── PaymentAmountFee.tsx
│   ├── payments.amount.$/ <= Matches any route not matched under /payments/amount/*
│   │   └── route.tsx
│   ├── payments.amount.autopay/
│   │   ├── route.tsx
│   │   └── AchPullModal.tsx
│   ├── payments.amount.$paymentType/ <= paymentType value can be used in code as param
│   │   ├── route.tsx
│   │   └── AchPullModal.tsx
└── root.tsx

```

There are a few things to note here:

* `_shared` is meant to be scoped in different levels. This makes it so you know how many different pages your code touches by just looking at the directory. For example:
* `_shared` goes across all the routes and will potentially affect a wide range of features
* `payments.amount._shared` is meant to go across only payments.amount. directories, so the blast radius will be limited
* This is meant to have compatibility with Remix and in turn will help organize your react router code
* For all other syntax regarding naming conventions, please [take a read here](https://remix.run/docs/en/main/file-conventions/routes)

### Benefits

The benefits of having a convention for the directory structure (besides aligning with the new architecture) are:

* A standardized way to organize your React code
* Clear boundaries of what code touches which pages (colocation)
* A clear understanding when you should be creating a new directory and what type
* The flexibility of creating as many files as you want as the directories will define the scope of those files

### Downsides

* Potentially long directory names
  * For example, a path with `maintenance/service_requests/1/work_orders/1` will map to a directory name with `maintenance.servce_requests.$serviceRequestId.work_orders.$workOrderId`
* This structure is supposed to work alongside using React Router v6
* Flat directory structure can make the `routes` directory extremely big and potentially a pain to scroll in.

<!---->

    routes/
      /route1
      /route1.sub_route1
      /route1.sub_route2
      /route1.sub_route3
      /route1.sub_route4
      /route1.sub_route5
      /route2.sub_route1
      /route2.sub_route2
      /route2.sub_route3
      /route2.sub_route4
      /route2.sub_route5
      ...etc

### Alternatives

There’s not many alternatives because we wanted to focus on having a directory structure that is compatible with the [Remix framework](https://remix.run/).

* [Remix-flat-routes](https://github.com/kiliman/remix-flat-routes)
  * Another option for a standardized directory structure that was a good candidate, but it’s not the “official” recommendation by the Remix team. Therefore, this documentation needs to be looked at in their own Github page as well as the Remix documentation to learn more about the conventions. Also, the recommended approach seems to be constantly changing.
  * As a side note, the recommendation in this doc is using `remix-flat-routes` under the hood, but it’s using the spec recommended by [Remix](https://remix.run/docs/en/main/file-conventions/routes#folders-for-organization). `remix-flat-routes` also has scripts to update the convention above if needed, so we can always update if we ever need to.
* Continue the way we’ve been doing things
  * This is fine and has been somewhat working for all of the past, but I have continuously seen many engineers restructuring their code to make more sense for their team. That might seem fine, but it does incur mental overhead for something that should be a convention. Bear in mind that every team has to either do this or not.
* Have a separate `/routes` and `/src` directory where `/src` is how we structure code today
  * Similar reasons to above
  * I also see colocation of code as very important for quickly knowing the importance of a piece of code. For example, a hook in a route directory will only ever span that route. We currently have lots of different practices for creating a hook, but one way we currently do this is having a global hook directory. This is true even if that hook only touches one file.
